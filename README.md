# sova-pyrus-bot

Бот для Pyrus, который следит за лимитами бюджета (форма «Бюджет БДР»)
и отмечает расходы, вышедшие за лимит.

## Что делает

- **Вебхук** (`POST /`). Pyrus присылает событие о комментарии в расходной
  задаче на первом этапе. Бот находит подходящий бюджет, списывает сумму
  с текущего «Остатка», ставит галочку «Превышение лимита» и отвечает
  `approved` / `rejected`.
- **По расписанию:**
  - каждый час в :00 — полный пересчёт: остаток = бюджет − все расходы;
  - каждый час в :30 — в «Остаток» записывается полная сумма бюджета;
  - раз в 12 часов — новый токен Pyrus.
- `GET /` и `GET /health` — проверка, что сервис жив.

Расход относится к бюджету, если совпадают статья расходов и подразделение,
а дата расхода попадает в период бюджета.

## Структура

```
main.py                  точка входа (uvicorn main:app)
app/
  config.py              ID форм, откуда что читать, переменные окружения
  pyrus/client.py        HTTP-клиент Pyrus API v4
  budget/
    models.py            Бюджет и расходы (dataclass-ы)
    parsers.py           JSON задачи Pyrus → модели
    rules.py             правила: подходит ли расход бюджету, списание лимита
    service.py           сценарии: пересчёт, сброс остатков, проверка расхода
  web/
    app.py               FastAPI, расписание, сборка зависимостей
    webhook.py           подпись Pyrus и ответ на вебхук
tests/                   юнит-тесты (pytest)
```

Зависимости идут в одну сторону: `web → budget.service → (rules, parsers, pyrus)`.
Правила и парсеры ничего не знают о сети, поэтому их легко тестировать.

## Запуск

```bash
pip install -r requirements.txt
uvicorn main:app --port 8034
pytest          # тесты
ruff check .    # линтер
```

Переменные окружения (можно положить в `.env`): `BOT_LOGIN`, `BOT_SECRET_KEY`,
`BDR_OVERLIMIT_ID` (поле «Остаток» в БДР), `ACCOUNT_OVERLIMIT_ID`,
`CASH_OVERLIMIT_ID`, `PAYMENT_OVERLIMIT_ID`, `CASH_NEW_OVERLIMIT_ID`,
`PAYMENT_NEW_OVERLIMIT_ID` (поля «Превышение лимита» в формах).

## Известные проблемы

При рефакторинге поведение сохранено **один в один**, включая перечисленное
ниже. В коде такие места помечены `(!)`. Каждое чинится отдельной правкой.

1. В пересчёте «новые» наличные и платежи читаются из **старых** форм,
   а сами новые формы не читаются (`config.RECALCULATION_SOURCES`).
2. В пересчёте платежи из старой формы учитываются **дважды** (там же).
3. По вебхуку счета и наличные **всегда согласуются**, даже при превышении:
   результат возвращается только для платежей (`BudgetService.check_expense`).
4. Новые формы ставят галочку в поле с ID старых форм
   (`Settings.overlimit_field_id`), `CASH_NEW_OVERLIMIT_ID` и
   `PAYMENT_NEW_OVERLIMIT_ID` не используются.
5. В :30 остаток сбрасывается на полный бюджет, и до :00 вебхук проверяет
   расходы против полного бюджета.
6. «Остаток» = 0 считается пустым и заменяется полным бюджетом.
7. Если Pyrus не ответил при чтении формы расходов, пересчёт идёт без неё
   и записывает завышенные остатки.
8. Если авторизация не удалась, токен сбрасывается до следующей попытки
   (через 12 часов).
9. Остаток бюджета записывается по разу на каждое списание (лишние
   комментарии в задаче БДР).
10. Бот отвечает текстом ошибки на любые события, которые не обрабатывает.
11. ID форм «Платежи новые» и «Наличные новые» одинаковые для dev и prod.
